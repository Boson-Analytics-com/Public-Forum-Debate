Public Forum debate tool — file-by-file reference

A flowsheet
for the whole pipeline.

In competitive debate, a flow is the running notes a debater keeps of every argument, answer, and drop in a round. This codebase automates that same discipline one layer earlier: it scrapes sources, turns them into a citation-verified evidence base, and then runs — and judges — full Public Forum rounds on top of it. Thirteen scripts, three stages of trust. Below is what each one actually does. 

sources.docx → extract_urls.py → fetch.py → parse.py → documents.jsonl
documents.jsonl → chunk.py → claims.py → index.py → kb.sqlite
kb.sqlite + resolution.json → debate.py / round.py / opponent.py / engine.py / judge.py

Everything reads and writes under ./corpus/. The codebase itself isn't consistent about calling a file's place in this a "stage" or a "step" — the tag on each card below is copied verbatim from that file's own docstring.

Before the pipeline — for readers new to PF

What Public Forum debate is

The rest of this page assumes you already know the format this tool automates. This section is that primer.

What is Public Forum Debate?

Public Forum Debate is a team debate format where two pairs of students argue for or against a current-events topic.

  • Team debate — two debaters per side (2 vs 2).
  • Focus on current events and public policy topics.

Goal of PF: persuade the judge your side wins.

Two audiences, two speeches

Lay vs. tech judges

Lay
A play on the word “layman.”

Someone who doesn't have experience in debate, or much experience — like a parent. They might be unfamiliar with jargon and nuance, and bad at flowing and/or following speed-reading (“spreading”).

Tech
Someone much more familiar with the technicalities.

Someone who debated throughout high school — VERY familiar with this style of debate, including “prog” (short for progressive arguments, like kritiks or shells).

Debate structure / round format

The seven parts of a round

1 · Constructive Speeches
4 min each
Present your team's main case/arguments.
2 · Crossfire
3 min
Direct questioning between speakers.
3 · Rebuttals
4 min
Respond to the opponent's arguments.
4 · Crossfire 2
3 min
Direct questioning between speakers, now over the rebuttals.
5 · Summary Speeches
3 min
Explain the key issues and what matters most.
6 · Grand Crossfire
3 min
All four debaters question each other.
7 · Final Focus
2 min
Final voting issues: why your side wins.

Part I — six files

Building the knowledge base

Everything here runs once per corpus and produces kb.sqlite — the thing the debate side is not allowed to contradict. Each step is resumable and idempotent by design, so a bad run costs minutes, not the whole scrape.

Stage 0 extract_urls.py

Link harvesting

Pulls every link out of a source document that's mostly prose — bare http(s):// URLs, scheme-less domains, markdown/HTML hrefs, links buried in a .docx's hyperlink relationships, and PDF link annotations. Nothing is dropped by default; filtering is opt-in via flags, so review happens before a single fetch runs.

reads sources.docx
writes urls.csv
Stage 1 fetch.py

Archival fetch

Downloads each URL's raw bytes and nothing else. Fetching is the expensive, rate-limited, irreversible step — pages change, paywalls tighten, sites disappear — so this script's only job is to grab and archive; parsing is cheap enough to redo as often as extraction improves.

reads urls.csv
writes corpus/raw/<sha1-of-url>.html.gz + manifest.jsonl
resumable — skips URLs already in the manifest
Stage 2 parse.py

Provenance extraction

Turns archived HTML into documents.jsonl with real provenance — publication date, author, section, headline come from <meta> tags and JSON-LD, not regex over prose. Its output carries an immutable normalized_text: every downstream quote is a (doc_id, start_char, end_char) offset into that exact string.

reads corpus/raw/*
writes documents.jsonl
touches no network — safe to re-run anytime
Step 4 chunk.py

Passage chunking

Cuts each document into ~300-word passages on sentence boundaries. Chunk text is sliced directly from normalized_text rather than rebuilt, which is what keeps start_char/end_char exact — and exact offsets are what make quote verification possible one step later.

reads documents.jsonl
writes chunks.jsonl
check: "Offset mismatches" = 0
Step 5 claims.py + claims_bedrock_opus.py

Claim extraction — this is the knowledge base

An LLM reads each chunk and extracts the arguable points as structured claims. Every claim must carry a quote copied character-for-character from the chunk; locate_quote() searches for it in the source text — exact match keeps the claim with offsets attached, no match rejects it and retries the chunk once. This is the entire fabrication guard, and it's backend-agnostic.

claims.py
Google AI Studio / Gemini
needs GEMINI_API_KEY, GEMINI_MODEL
claims_bedrock_opus.py
AWS Bedrock, Claude Sonnet 5
needs AWS credentials, BEDROCK_MODEL_ID
reads chunks.jsonl
writes claims.jsonl + claims_report.json
quote-verification guardrail retry-once on rejection

Naming quirk: despite the generic filename, claims.py's own docstring calls itself the "Gemini variant" — README.md's pip install anthropic setup instructions describe the original, no-longer-checked-in design.

Step 6 index.py

Hybrid indexing & retrieval

Builds kb.sqlite and serves search over it: SQLite FTS5/BM25 keyword search fused with sentence-transformer embeddings via reciprocal rank fusion — embeddings are optional and it falls back to keyword-only without them. Every result carries a tier (direct / related / none) computed from absolute cosine-similarity and query-word coverage, not raw RRF rank, because a top garbage match can rank like a top perfect one.

reads claims.jsonl
writes kb.sqlite
"none" tier returns empty on purpose
Part II — two files

Running the debate

Everything here argues, attacks, or scores — always by pulling from kb.sqlite, never by inventing evidence mid-round. The tool deliberately never does live web search here; that would bypass quote verification entirely.

Step 7 debate.py

Argument generation

case builds a constructive from the strongest claim clusters per contention tag, diversified across sources so no single card can kill three contentions at once. respond answers one opponent argument, branching prompt style on evidence strength: strong (quote it), thin (reason first, cite lightly), none (reason only). Every none response is logged to gaps.jsonl as a weak spot in the corpus.

citation guard — regenerates once, then hard-blocks
Step 9 round.py

Round state & PF debate orchestration

Holds the memory debate.py doesn't have — which contentions ran, which were attacked, what's already conceded. It runs two independent modes on purpose, in separate state files so they can never collide:

corpus/round_state.json Self-play harness state — start/speech/attack/status — used by engine.py for KB calibration.
corpus/debate_state.json Symmetric PF mode — a human picks a side, the tool argues the other, both go through the real 11-step order.

The real Public Forum order, as walked by debate-run:

1Constructive 2Constructive 3Crossfire 4Rebuttal 5Rebuttal 6Crossfire 7Summary 8Summary 9Grand crossfire 10Final focus 11Final focus
pro speech con speech both sides, live

All of it accumulates into one argument graph (st["attacks"]) that both the summary/final-focus builder and debate-status read to determine what's conceded, held, or contested. Archives to corpus/debates/debate_<started_at>.json — the filename is stable across resumes.

Part III — when a person is in the round

The human turn

engine.py run/batch never involve a person — opponent.py generates every attack. Add --human-side (via round.py debate-* or engine.py debate) and a real person types the questions, answers, rebuttals, and closing speeches instead. What follows traces those actual keystrokes through the code, stage by stage: which function catches what you type, what it checks — and, just as importantly, what it doesn't.

1

The side door (manual, easy to miss): the older self-play CLI. python round.py incoming --text "..." and python round.py attack --text "..." both take free text on the command line — normally opponent.py supplies it automatically during a self-play round, but nothing stops you from typing --text yourself. incoming() hands your text straight to debate.py's respond() — the same pipeline described under Crossfire below — and prints a real answer. attack() only logs your text and grades it (kb.rebut()) for later weighing; it never generates a response at all.

2

The real door: the symmetric PF debate. Everything below assumes this path — round.py debate-start / debate-run, or engine.py debate --human-side pro|con.

PF steps 1–2 · pro, then con

Constructive

One hard question, no default: _ask_kb_or_own() asks "Build your {SIDE} case from the knowledge base, or write your own contentions? [kb/own]" and re-prompts on anything that isn't exactly kb or own.

You type
  • kb — nothing further to type; your case becomes case_{side}.json, verbatim.
  • own — paste your entire speech in one shot, ended with a line that's just END (_collect_multiline()).
→
What happens to it (own)
  • debate.py's extract_contentions_from_speech() asks the model only for line-number ranges — never to reproduce your words — so each contention's text is sliced straight out of your own paste. Verbatim by construction, not by checking afterward.
  • The one thing the model does reproduce is a short quote, if a contention claims one. That gets checked as a substring of your whole paste; one it can't find gets silently dropped.
  • KB backfill is offered unconditionally: any strong KB area you didn't cover gets listed, and you choose yes/no.
  • An empty paste (or zero contentions after a declined backfill) restarts this whole stage — pick_target() downstream indexes into contention #1 unconditionally and would crash with IndexError on an empty case.
quote checked against your full paste
Not checked: only the quote field goes through any verification. Your claim, your warrant, your impact — none of it is checked against the knowledge base or anything else. You could argue something the corpus flatly contradicts and own mode accepts it as written.
PF steps 3, 6, 9 · crossfire_1, crossfire_2, grand_crossfire

Crossfire

Asker and answerer alternate every exchange, up to --exchanges volleys (default 6), ending early on "Continue? [Y/n]". The target contention is never asked for on either side — it's auto-picked as whichever opposing contention has been hit the fewest times so far (your turn: _pick_target_contention(); the tool's turn: pick_target()'s attack-count-first sort — same spreading principle, both directions).

when it's your question

You ask
  • _collect_multiline() collects your question; a blank re-prompts until you type something.
  • Logged straight into the attack graph — no evidence attached. attack_evidence_used: []: "human questions aren't tied to KB claim_ids (yet)."
→
The tool answers
  • _debate_tool_answers() first runs validate_query(): under 4 words, or a placeholder like "the argument"/"test", gets deflected with a canned line — instead of the SystemExit the standalone CLI would raise, which would otherwise kill the whole multi-stage debate over one throwaway line.
  • Otherwise debate.py's respond(): retrieves your side's real evidence against your question (kb.rebut()), grades it strong / thin / none, and drafts an answer in that register.
  • On a none answer only: scans its own text for fabricated-looking years/percentages/studies, regenerates once, hard-blocks with a canned refusal if it still fabricates — and logs the gap to gaps.jsonl.
citation guard (tool's answer only)

when the tool asks you

The tool asks
  • _debate_tool_asks() reuses opponent.py's do_attack() in reverse — same pick_target() spreading, same KB retrieval against your side.
  • Citation guard, plus a second, independent check: the mechanism-swap guard (_mechanism_guarded()) — a checker call asks whether the attack argues the resolution's actual mechanism or quietly swapped in a different policy. One retry, then a mechanism_swap_flag if it's still swapped.
  • Stage-aware: crossfire_1 attacks your constructive, crossfire_2 attacks your rebuttal, grand_crossfire attacks your summary — and it's shown its own asker-side speech too, so it compares rather than reacts blind.
citation guard mechanism-swap guard
→
You answer
  • _collect_multiline() again.
  • Marked answered = bool(your_text.strip()) — that's the entire check. Not graded for relevance, evidence, or whether it actually addresses the question.
no strength grading on your answers
PF steps 4–5 · pro, then con — fixed order

Rebuttal

You type
  • Same paste-until-END collection, but via the raw debate_ask() loop directly — not _collect_multiline(). This is the exact function still exposed to the bracketed-paste desync bug noted elsewhere in this codebase.
  • Logged as one attack against the auto-picked target contention. response/answered start as None — not "unanswered," genuinely not-yet-evaluated.
raw input() — no paste-safety helper
→
The tool's rebuttal — two jobs, one speech
  • do_rebuttal_speech() attacks every one of your contentions by name — one KB lookup each, with claim_ids already used by an earlier contention stripped from later ones, so the same card can't cover two sections of one speech. Explicitly not mechanism-guarded: that checker compares one text to one contention, and doesn't fit a speech covering several.
  • Then _debate_tool_answers() loops over every still-open hit on the tool's own case (skipping anything already answered live in crossfire) to actually defend it. The two halves are joined by an explicit transition line, not just concatenated.
citation guard (per-contention) no mechanism-swap guard here
Turn-order quirk: whether your rebuttal-attack gets an in-round answer depends on which side you're arguing, since rebuttal is always pro-then-con. Argue pro, and the tool's (con's) rebuttal comes right after yours and picks your attack straight out of its unanswered hits. Argue con, and the tool's (pro's) rebuttal already ran before you typed anything — your rebuttal-attack can sit at answered: None for the rest of the round unless a later crossfire happens to land on that same contention.
PF steps 7–8 and 10–11

Summary & Final Focus

The two stages where nothing you type is examined at all — by either side.

You type
  • Same raw debate_ask()/END collection as rebuttal.
  • Stored completely verbatim, source: "human". No extraction, no quote check, no citation guard — nothing runs on it. Whatever you typed is exactly what reaches the transcript, and the judge.
zero verification of any kind
→
The tool's closing speeches
  • Summary: DEBATE_SUMMARY_SYSTEM is built from the actual accumulated speech text already on record — both sides' constructive and rebuttal, pasted directly into the system prompt — not a fresh KB lookup.
  • Final focus: same shape, built from both sides' summaries plus a condensed grand-crossfire highlights reel (truncated per exchange).
  • Both are told, in the prompt, to only reference material already introduced this round. That's an instruction, not a code-enforced check — debate_summary_or_final() never calls the citation guard at all.
no citation guard on either speech, either side
Cross-cutting

Configuration & guardrails

Model choice, cost controls, and the one dependency that's easy to miss.

Auth
Standard boto3 credential chain — exported env vars, ~/.aws/credentials, or an IAM role. Not ANTHROPIC_API_KEY.
BEDROCK_MODEL_ID
Shared model id for round.py, debate.py, opponent.py, judge.py, claims_bedrock_opus.py — currently amazon.nova-pro-v1:0. No file hardcodes a fallback anymore; each one exits with a clear message if this is unset, instead of silently defaulting.
OPPONENT_BEDROCK_MODEL_ID
Optional override so the opponent can run a different/stronger model than the tool. Falls back to BEDROCK_MODEL_ID when unset.
GEMINI_API_KEY / GEMINI_MODEL
claims.py only — a separate vendor with its own credentials, unrelated to the Bedrock config above.
--mock
Supported everywhere. Skips the real model call entirely — synthetic responses, no cost, no credentials needed — to validate pipeline wiring before spending anything.
MAX_TOKENS_SCALE
A 0.5 cost knob halving every real call's max_tokens ceiling, set in five files (debate.py, round.py, opponent.py, claims.py, claims_bedrock_opus.py). Bump each back to 1.0 before a production run.
